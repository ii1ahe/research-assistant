               --json artefacts/bench.json

Why LLM_MODEL is set: the free tier allows 20 synthesis requests per day per
model, and a two-mode sweep costs 12. The default model's allowance was spent
during the Phase 6 demo run and the first attempt at this benchmark, so the run
below used a model whose allowance was untouched. Retrieval never calls the LLM
at all, so the retrieval figures — the headline — are unaffected by the choice;
both modes below used the same model, so the comparison is unaffected too.

The --pause 10 is likewise a free-tier allowance, not part of the design. It
waits between questions and never inside one, so it cannot contribute to a
per-question timing; it shows up only in the sweep wall clock, which is why
that row reads ~83s in both modes. See the docstring of scripts/bench.py.

Two earlier runs are worth recording, because the failures say more than the
success does.

Run 1 — default model, no pacing. Retrieval came back clean (2.69x), but
synthesis failed on 1 of 6 questions in the sequential sweep and on all 6 in the
concurrent one, with HTTP 429 from the provider. The end-to-end row of that run
compared five real syntheses against five refusals, and reported 4.65x. It was
not a valid comparison and is not quoted; the benchmark now withholds that row
whenever synthesis did not complete, and exits 1.

Run 2 — after setting SYNTHESIS_TIMEOUT_SECONDS to 30. Sequential answered 5/5.
This is the run that found the deadline defect: synthesis had been running under
PER_SOURCE_TIMEOUT_SECONDS, ten seconds, and against the configured model it was
already failing roughly one call in six on a quiet machine — 2.9s, 3.9s, 6.1s
and 7.6s, then a timeout. The concurrent sweep answered 4/5, the last question
refused for rate rather than for time, which is what prompted the --pause option.

The run above is the first with all three constraints satisfied: a synthesis
budget the model can meet, enough daily allowance, and pacing between questions.
